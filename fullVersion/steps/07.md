# BC App Build Routine — 07 — Compile and Package, Troubleshoot, Iterate

**Runbook version:** 5.9.1.0 · Full edition · Phase: BUILD

> One step of the OCPF BC Agentic Development Framework runbook, fetched into `ocpfFramework/runbookSteps/` at the
> routine's first step and read **in full** the moment this step starts. The core runbook
> (`CLAUDE.md` or `.github/copilot-instructions.md`) carries only this step's stub; its Operating
> Rules and ALL ALONG sections apply throughout. **Standards §** is
> `ocpfFramework/standardsGuide/ocpfALDevStandardsGuide.md`; **Ops §** is `ocpfFramework/opsGuide/ocpfOperationsGuide.md`.

---


**Role:** the **pre-review**, right after the first clean compile and before the first package, is
done by the **reviewer sub-agent** — the project-local `ocpf-reviewer`, on the Main model and effort,
in the background (Operating Rule 10; Ops § Roles → *The pre-review*); root-cause diagnosis (the three questions below)
is done by the **reasoning role** (Operating Rule 10); the main role applies the resulting fix and does the
ChangeLog/TDD bookkeeping, and is also the one who compiles, packages, keeps
`docs/4-prove/SandboxInstall.md` current, and waits for the human to install each build. Same division for any bug surfaced later during PROVE-phase
testing (see Testing Feedback Log, ALL ALONG) — diagnosis is a reasoning-role task, fixing is the
main role's.

**Inputs:** Every batch from Step 06 (lint-clean, not yet compiled); the symbol-verified lint findings accumulated across BUILD; `docs/2-design/TDD.md`; ChangeLog.

**Actions:** First, **compile the whole extension once, with the analyzers this framework requires, then package it** (Operating Rule 4; Ops § Analyzers — check for an already-provisioned runtime before installing anything, Operating Rule 6b). This is Operating Rule 4's mandatory compile-and-package. Package naming, location (`outputAppPackage/`), the never-delete rule, version numbers, and Schema Sync Mode/Force Sync guidance all apply from this very first package onward (**read Ops § Packaging, including *Version numbers*, now**) — there is no "not a real package yet" grace period.

**The first build of a new app goes out at `0.0.0.1`, the version Step 01 wrote — no increment.
Before every build after it, in any step, increment the Revision first.** An existing app's first
build increments from the installed version, and every build after it increments again. The test:
if `outputAppPackage/` holds no package yet and `app.json` says `0.0.0.1`, build as is; otherwise
read `version` from `app.json`, add one to the fourth segment, write it back, then build —
mechanical, no approval, no ChangeLog entry of its own (ALL ALONG → Packaging & Versioning). **Never build twice at one version.** If `outputAppPackage/<Name>_<version>.app`
already exists, increment again; `ocpfFramework/scripts/al-analyze.*` refuses to overwrite an
existing output file (exit code 4, naming the file) — that refusal means the increment was
skipped, not that the file should be removed. Major, Minor, and Build bumps stay proposed and
approved (Rule 6a). Why: testers upload packages as PTEs through the Admin Center or Extension
Management, and a version already installed can never be uploaded again.

**Between the first clean compile and the first package: the pre-review** (Ops § Roles → *The
pre-review*). The moment the whole extension first compiles with the analyzers at 0 / 0, and
**before** the first package is built, delegate a read of every file under `src/` to the
project-local **`ocpf-reviewer`** — Main model and effort, in the background, the model passed on
the call, the report's `Model:` line checked against §1.7 before anything in it is used (Operating
Rule 10). Brief: the project root, `src/`, `docs/2-design/TDD.md`, `docs/3-build/BuildPlan.md`,
`docs/1-define/ProjectParameters.md`, the Standards Guide path with §1.1–§1.9, Part 2, §5.3–§5.4,
Part 7, Part 11, §8.3, `ocpfFramework/patterns/`, the symbol source — nothing else. It returns
findings in two tiers (what would break the human's first sandbox test or force a rebuild; what is
worth fixing before the package), observations, and what it could not verify; it grades nothing.
**Present every finding in one message** — file and line, root cause, proposed fix — and ask once
(Rule 6a): **Apply all (recommended)** / **Apply selected** / **Discuss first**; a finding that
would change the FRD, the TDD, or a design rule gets its own box. Nothing is applied before the
answer. Apply the approved fixes, recompile to 0 / 0, and record **each finding with its decision**
— applied, declined and why, deferred to Step 09 — as an Issue entry in `docs/0-project/ChangeLog.md`
(source *Pre-review*), with the model that ran; note the pass in `docs/0-project/ProjectMemory.md`.
Then build the first package. A report with no findings is one ChangeLog line saying so. The
pre-review runs once per Step 07, not per round; Step 09's Code Review is the full review.

**After every build, end the message with the fixed block, on its own lines — never paraphrased,
never folded into prose:**

```
Package built: outputAppPackage/<Name>_<version>.app (previous build <version-1>)
Schema: additive only → upload with Schema Sync Mode = Add
   or: <what was removed / shrunk / retyped / re-keyed> → upload with Schema Sync Mode = Force Sync
       (Microsoft: test a forced sync in a sandbox first; it can lose data in <where>)
Install: you upload it — docs/4-prove/SandboxInstall.md, §1 updated for this build.
Then: tell me the version and environment you installed; I record it as the last installed version.
```

The schema line compares this build's objects against **the last package installed in a tenant**
— not the previous build — so record "last installed version" in `docs/0-project/ProjectMemory.md`
and the ChangeLog each time the human confirms an upload, and read it here.

**After every compile with 0 errors, check what the human's editor shows** (ALL ALONG → Keeping
the Editor in Sync). If VS Code still marks AL errors the compiler
didn't report, such as an object ID "outside the allowed ranges" or a symbol that "is missing",
the editor's view is stale, not the code. Refresh the view; never change code that compiles
clean to make stale red marks go away.

**From here, Step 07 is a cycle, not a single event.** Packaging is not a milestone held back for later — it happens every time the extension changes during troubleshooting:
1. **The human installs the current package in a BC sandbox — the agent never uploads unprompted and never offers to.** With the first package, write `docs/4-prove/SandboxInstall.md` from its template (Ops § Packaging → *The sandbox install guide*; Ops § Documents): Microsoft's two upload routes step by step, and §1 naming this build's file, version, Schema Sync Mode, sandbox, and dependencies. After every later build, rewrite §1 only. Then wait: the round continues when the human says which version they installed and where, and that answer is recorded as the last installed version in `docs/0-project/ProjectMemory.md`. Never assume the upload happened, and never offer to do it. If the developer explicitly asks for a publish, confirm first that they mean a DEV extension to the named sandbox, then do it (Ops § Packaging → *Publishing on explicit request*) — once, on request, never as the routine.
2. Test it — manually, by the human. **Every round's manual test includes the two Standards §11.3 client checks**: create a child from *every* parent entry point (each part and each action) and confirm it stays visible with the link field filled and the unfiltered child list has no blank-link rows; open the wizard and the setup card and confirm the number-series field opens the *No. Series* dropdown, the pick survives Finish, and the first two records number consecutively. *"The view is filtered, and the entry is outside the filter"* and a series field with no dropdown are defects to diagnose (Standards §11.1, §11.2), never warnings to dismiss — ask the human to report them explicitly rather than clicking past them.
3. For every error, warning, or reported problem, **first check `ocpfFramework/patterns/` (ALL ALONG → OCPF BC AL Patterns Library)** for a matching, already-documented pattern — a previously-solved bug class should be a fast recognition, not a fresh investigation. If nothing matches, ask the three questions (Operating Rule 4's systemic-signal discipline):
   - **A System.AI or Copilot error** (an obsolete `RegisterCapability` overload, a GPT-4o getter, "Copilot capability has not been set", AL0223 on the dialog): check the Blueprint's `references/08-api-reference-bc27.md` and `references/09-false-assumptions.md` before memory (ALL ALONG → *Business Central Copilot Features*).
   - **One-off or pattern?** Search all generated files for the same class of issue before fixing one instance.
   - **Where did it come from?** Trace to the generation rule, the TDD template, or the source data.
   - **What rule should have caught it?** Fix that rule or the pre-flight check.
4. **Approve the round's fixes together, then apply them.** Once every problem from this test round has a diagnosis, present them all in one message — each listed separately with its root cause, the rule or template it traces to, and the proposed fix — and ask once (Rule 6a): **Apply all** / **Apply selected** (the human names which) / **Discuss first**. Nothing is applied before that answer. **A diagnosis that would change the FRD, the TDD, or a design rule gets its own separate box**, never folded into the bulk approval. Then fix each approved **root cause** (rule / template / filter), regenerate the affected files, and log each issue + resolution in the ChangeLog before moving on. Update the TDD whenever a rule changes.
5. **Increment the Revision, compile and package again, with the same analyzers, and end with the "Package built:" block**, rewrite `SandboxInstall.md` §1, the human installs it, retest. Repeat steps 1–5 until the extension compiles with 0 errors / 0 warnings and the human confirms sandbox testing is clean. Every round leaves its own package in `outputAppPackage/`; none is ever overwritten.

**Translations are part of this cycle, from the first full build onward** (skip if Parameter §1.9
chose *US wording, no translation files*). **The cycle itself is Ops § Translations — read it at the
first full build.** In short: every build syncs the target files, verifies any new BC term, and runs
the problem checks; drafting, the full checks, and per-language testing wait until the source text is
stable — the first build the human confirms clean on the sandbox, again before this step closes, and
again after any later fix that changes source text. Reviewers work in parallel; approval is required
only at Step 12.

**The API test checklist** — defined once, here, and used twice over the rest of the routine: as the source Step 11 writes `docs/4-prove/HumanUnitTestScript.md` from, and authoritatively by humans at Step 12 (Release to Users for Testing):
- **Green-team (happy path):** `$metadata` returns the expected schema; read a collection; read a single record by `SystemId`; create a record on an editable endpoint; update a field; confirm a read-only endpoint rejects writes. Endpoint URL shapes are in Standards Appendix A.
- **Red-team (boundary):** write to a read-only endpoint; send a non-existent field; send an invalid key; delete a record with dependencies; call with missing permissions — confirm each fails *gracefully with a clean, actionable error*.

**The checklist is the human's to run, every round — the agent does not test on the sandbox.** It
never uploads a package, so it never has a build to call; and the AL MCP Server has no tool that
calls a published endpoint anyway (16 tools, verified on AL extension 18.0.2732683). Say so plainly
if asked, rather than improvising a route. Suggest the tools a person tests APIs with: **Postman**,
or a low-code caller like **Power Automate**, **Power Apps**, or **Copilot Studio**. **Endpoint URL
shapes are Standards Appendix A** — including the company segment most endpoints need. Step 12's
human pass, after Code Review and documentation have had their say, is the authoritative one.

**Remediation — when the design has to change after this step closed (Ops § Usage & Cost →
7).** If testing at Step 08 or Step 12, or a late requirement change, means the FRD and the TDD
must be redone and objects regenerated — not a fix inside this step's cycle — open a
**remediation** the moment the human agrees it is a rebuild: window `07a` (then `07b`, …) titled
*Remediation — <what changed>*, row `| BUILD | 07a — Remediation | In Progress |` directly under
this step's row in `ProjectProgress.md`. Redo the FRD and TDD in place (ChangeLog entry naming
the remediation), regenerate, and bring the extension back to 0 / 0 under that window; close it
with its usage rows and the Rule 6c box offering the step the project came from. The dashboard
shows it as `07a · Remediation` on the journey line.

**Outputs:** All batches compiling and packaging with **0 errors, 0 warnings**; one package per build in `outputAppPackage/`, each at its own Revision, each announced with the "Package built:" block; `docs/4-prove/SandboxInstall.md` written with the first package and its §1 current; at least one package installed by the human and manually tested on a sandbox, with "last installed version" recorded; ChangeLog current; TDD updated for every rule change; every target translation file synced, drafted, and passing technical checks, with the glossary current.

**Exit gate:** Full extension compiles clean, with the analyzers and nothing suppressed (Ops § Analyzers); the pre-review ran on the Main model before the first package (its report's `Model:` line checked), every finding was decided in the options box and recorded in the ChangeLog with its decision; the human confirms sandbox testing is clean; no known systemic issue outstanding; `app.json`'s version equals the last package built and no two packages in `outputAppPackage/` share a version; ChangeLog and TDD reconciled (Operating Rule 5); no translation unit in any language required at first release is in `needs-translation` or `needs-adaptation`, and the technical translation checks are clean. This step's usage rows — one per model in Claude Code, one per step in Copilot — are written before this message (Operating Rule 11).

**Step close (Rule 6c) — mandatory, never a prose prompt:** once the exit gate is met and the usage rows are pasted, end the closing message with the options box: **Proceed into Step 08 now — closes BUILD, opens PROVE (recommended)** / **Stop here** (say what there is to review and how to resume). Nothing of Step 08 starts until the human answers.
