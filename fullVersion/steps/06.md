# BC App Build Routine — 06 — Code Generation

**Runbook version:** 5.1.0.0 · Full edition · Phase: BUILD

> One step of the OCPF BC Agentic Development Framework runbook, fetched into `ocpfFramework/runbookSteps/` at the
> routine's first step and read **in full** the moment this step starts. The core runbook
> (`CLAUDE.md` or `.github/copilot-instructions.md`) carries only this step's stub; its Operating
> Rules and ALL ALONG sections apply throughout. **Standards §** is
> `ocpfFramework/standardsGuide/ocpfALDevStandardsGuide.md`; **Ops §** is `ocpfFramework/opsGuide/ocpfOperationsGuide.md`.

---


**Role:** in **parallel mode** (the Step 05 batch-mode answer), each batch is written by a
**generator sub-agent** — the project-local `ocpf-generator`, on the Main model and effort
(§1.7), one per batch, in the background — and pre-flighted by the **light role** as it returns;
the **main role** integrates: Object Register, ChangeLog, deviations, and every fix. In sequential
mode the main role generates each batch itself and the light role pre-flights it, as before.
Whatever the mode, the generator never edits the ChangeLog, the Object Register, the TDD, or
another batch's files — it writes its batch's files under `src/`, reads its brief only, and
reports deviations and open questions back. **Full procedure: Ops § Roles → *Generation speed*
and *Parallel batches*.**

**Inputs:** `docs/2-design/TDD.md`, `docs/1-define/ProjectParameters.md`, symbol file, `docs/3-build/BuildPlan.md` (IDs and `src/` file names already fixed per batch), pre-flight checks, the batch mode and fast-mode answers from Step 05.

**Actions — the three modes, then the speed rules that apply to all of them:**

**Parallel mode (recommended, two or more batches, harness runs sub-agents):**
1. **Confirm nothing is left to decide.** The Build Plan fixes every object's ID and file path, and the batches are disjoint, so no two generators can touch the same file or the same register row. Run the Step 05 **pre-generation** pre-flight pass on every batch's planned names/fields now, all batches at once (main role — TDD housekeeping); fix the TDD before any generator starts if anything fails.
2. **Start one background generator per batch, all at once** — the project-local `ocpf-generator` definition, model passed explicitly (Operating Rule 10), run in the background (Ops § Roles → *Enforcement*, *Run delegations in the background*). **The brief carries everything the generator needs and nothing else:** this step file's generation rules (Action 4 of sequential mode, verbatim), the batch's own TDD sections and its rows of the Build Plan, `docs/1-define/ProjectParameters.md`, Standards §1.1–§1.8 and §2 as exact text — and, when the batch has a child list or list part, a setup page, or a wizard, Standards Part 11 and the matching `ocpfFramework/patterns/` files — the standard object template text, and the symbol source (the `.alpackages/` path, plus the extracted source-table and field data for the batch's objects). Never the core runbook, never a whole guide, never the conversation. The generator returns one summary: files written, deviations, open questions.
3. **As each generator returns, run the Step 05 post-generation pre-flight pass on that batch, in the background, while the others continue** — the **light role**, delegated on the §1.7 model (Operating Rule 10): findings only, it does not edit code, plus a manual read against the AZ AL Dev Tools rules (Standards Appendix C). Symbols are verified here, once per batch. **Do not invoke the AL compiler** (Operating Rule 4).
4. **The main role integrates each batch as its pre-flight comes back:** apply every finding, log every deviation the generator reported or the pre-flight found (Operating Rule 7), update the Object Register, commit the batch. A pre-flight failure the TDD doesn't answer, or a deviation from the TDD, stops for the human on that batch only (Rule 6a) — the other generators keep running. The human can say "stop" at any time.
5. Once every batch is generated, pre-flighted clean, and committed, move to Step 07.

**Sequential mode (*One batch at a time*, *Ask me before each batch*, or a harness that can't run parallel sub-agents — say which):**
1. **Approval, per the Step 05 answer.** Before the first batch, the batch plan approval from Step 05 applies. If the human chose **Ask me before each batch**, pause for approval before each one. Otherwise continue from batch to batch without asking, and stop for approval only when a pre-flight check fails in a way the TDD doesn't already answer, or generation has to deviate from the TDD (log the deviation per Operating Rule 7 first). The human can say "stop" at any point.
2. Extract source-table and field data for this batch's objects from the symbol file.
3. Run the Step 05 **pre-generation** pre-flight pass on the planned names/fields (main role — this is TDD housekeeping, distinct from the file-level lint in Action 5 below); fix the TDD before generating if anything fails.
4. Generate the batch's AL files, under `src/` at the paths the Build Plan fixed, from the standard template (Standards §1.3), substituting only Step 01 parameter values. Every file: one `namespace` (omitted entirely if Parameter 1.1 `Use Namespace` = `No`), one `using` (from symbol file), `ODataKeyFields = SystemId`, exactly one of `DelayedInsert = true` / `Editable = false`, and `Caption` + `ToolTip` + `ApplicationArea = All` on every field (Standards §1.1–§1.4, §2.1–§2.6). Captions and ToolTips written as self-describing schema for API consumers (Standards §2.5–§2.6), in single-language label syntax only — never `CaptionML`, `ToolTipML`, any other ML property, or `TextConst` (Standards §1.7). Every message a `Label` per Standards §8.3, source wording per Parameter §1.9 and the glossary, API caption locking per the Step 03 decision (Standards §8.6). **Source text only** — no translation file is created or edited during generation; translation starts at Step 07, once a build has produced `.g.xlf`. No dead code, no empty triggers, no commented-out fields, no `// TODO` (Standards §1.5).
   **Client pages are not API pages and have their own rules (Standards Part 11), applied while writing, not found in the sandbox:** every child list or list part gets the six elements of §11.1 (property link, hidden link control, two-group `OnNewRecord` read, `TestField` in the table's `OnInsert`, `DelayedInsert = true`, no `Init()` after seeding); every number-series field gets `TableRelation = "No. Series"` on the setup table and the wizard bound to a temporary copy of it, and numbering uses codeunit `"No. Series"` (§11.2). Read the matching `ocpfFramework/patterns/` files first, as the batch plan says (Step 05).
5. **Run the Step 05 post-generation pre-flight pass on the batch immediately** — dot the i's, cross the t's on each file as you go, plus a manual read against the AZ AL Dev Tools rules (Standards Appendix C). This pass is done by the **light role**, delegated on the §1.7 model, in the background (Operating Rule 10) — it reports findings only, it does not edit code; the main role applies every fix. **Do not invoke the AL compiler** (Operating Rule 4).
6. Do not proceed to the next batch until this one's pre-flight (including symbol verification and Standards §5.3 permission-set coverage) is clean. Once every batch in the plan is generated, move to Step 07 (Operating Rule 4).

**Speed rules — every mode, every generator, the main role included** (Ops § Roles → *Generation speed*):
- Generation runs at the Main role's recorded effort — Medium by default; nobody raises it for code.
- **One complete file per Write call**, never incremental edits to a file that is being created.
- **No narration between files** — one summary per batch: files written, deviations, open questions.
- **The brief carries the exact template and Standards text**, so no guide is re-read per file.
- **Symbols are verified once per batch by the light pass**, not per file during generation.
- With Opus as Main in Claude Code, fast mode was offered once at Step 05; honour that answer, don't ask again.

**Outputs:** Generated AL files for every batch under `src/`, each lint-clean including symbol verification; updated Object Register; ChangeLog entries for any deviation, naming the generator's model where a batch was delegated (Operating Rule 10); one commit per batch. The extension is **not** compiled as part of this step (Operating Rule 4) — that happens next, in Step 07.

**Exit gate:** Every planned object generated at the ID and `src/` path the Build Plan fixed; each batch's pre-flight (including symbol verification and permission-set coverage) was clean before it was integrated — before the next began, in sequential mode; every generator's report opened with the Main model and was checked against §1.7 (Operating Rule 10); the Object Register and ChangeLog are current for every batch. No compile is required here — Step 07 compiles next. This step's usage rows — Main, light, and generator models each on their own row — are written before this message (Operating Rule 11).

**Step close (Rule 6c) — mandatory, never a prose prompt:** once the exit gate is met and the usage rows are pasted, end the closing message with the options box: **Proceed into Step 07 now (recommended)** / **Stop here** (say what there is to review and how to resume). Nothing of Step 07 starts until the human answers.
